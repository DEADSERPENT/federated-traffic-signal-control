FILE: src/traffic_generator/intersection.py                         SCORE: 8/10
  Purpose : Models a single 4-way intersection (4 lanes, 2-phase signal).
  Strengths:
    - Clean dataclass design (Lane, Intersection, SignalPhase enum).
    - Poisson and uniform arrival distributions supported.
    - Phase-state machine correct (GREEN → YELLOW → phase-switch).
    - get_feature_vector() returns consistent 6-dim array used everywhere.
  Issues:
    - Lane.remove_vehicles() calls list.pop(0) — O(n) per vehicle.
      With queue_length up to 50 and 4 lanes × N intersections × T steps,
      this is fine now but will degrade with larger simulations.
      Fix: use collections.deque.
    - Actuated controller bug dependency: phase_timer is NEVER reset when
      phase switches (line 261 "self.phase_timer = 0"), but ActuatedController
      line 165 keeps incrementing it externally without reset — the
      "current_green_time" parameter to get_green_duration() is therefore
      always the cumulative run time, not the current green phase duration.
  Interlinking: Used by generator.py, all baselines, and scripts.

FILE: src/traffic_generator/generator.py                            SCORE: 7/10
  Purpose : Generates synthetic (X, y) training data via intersection simulation.
  Strengths:
    - Config-driven (YAML or dict or defaults).
    - get_all_intersections_data() supports FL client data splitting.
    - Non-IID achieved naturally: each intersection gets a random arrival_rate.
  Issues:
    - _calculate_optimal_green() is the ground-truth label generator.
      It is a HAND-CRAFTED heuristic (not from real data or a known optimal
      policy). This is the training target for the entire FL system — its
      quality directly bounds model performance. There is no validation that
      these labels minimize real waiting time.
    - get_intersection_data() is called at train time AND test time (local_ml.py
      line 219): test data is freshly generated, not a held-out split.
      This means evaluation MAE may be overly optimistic (test labels come
      from the same stochastic process with same seed state — not truly held-out).
    - arrival_rate sampled with np.random.uniform at init — not seeded by
      intersection_id, so different runs get different data distributions
      unless set_global_seed() is called first (not guaranteed call order).
  Interlinking: Used by local_ml.py, adaptive_fl.py, centralized_ml.py,
                run_ieee.py, run_byzantine.py.

FILE: src/federated_learning/aggregation.py                         SCORE: 7/10
  Purpose : FedAvg, Median, Trimmed Mean, Krum, Multi-Krum aggregation.
  Strengths:
    - All five Byzantine-robust strategies implemented correctly.
    - multi_krum_aggregate selects f+1 "good" models (correct per Blanchard 2017).
    - trimmed_mean_aggregate clips top/bottom k values per parameter.
    - AggregationStrategy enum provides type-safe strategy selection.
  Issues [PERFORMANCE]:
    - _compute_distances() uses nested Python loop: O(n²) × O(d) per aggregation
      where d = param dimensions. For n=9 clients this is fine. At n=100+,
      this becomes a bottleneck. Should use numpy broadcasting:
        diffs = params[i] - params[j]  →  np.linalg.norm(diffs)
      or scipy.spatial.distance.cdist for the full matrix.
    - All aggregation operates on CPU numpy arrays even when GPU is available.
      For large models, these numpy operations could run on GPU via torch.
    - AggregationStrategy enum defined here but run_byzantine.py passes string
      literals ("fedavg", "quality_aware") to adaptive_fl.py — enum is UNUSED.
      The string-to-dispatch logic is fragmented across files.
  Interlinking: Called by adaptive_fl.py (via robust_aggregate). NOT called
               directly by run_ieee.py or run_byzantine.py.

FILE: src/baselines/adaptive_fl.py                                  SCORE: 8/10
  Purpose : Main FL controller — FedProx, quality-aware aggregation, simulation.
  Strengths:
    - FedProx proximal term with μ=0.05 prevents client drift.
    - Quality-aware aggregation: α_k = n_k × (L_k + ε)^(-1) is novel contribution.
    - Patience-based early stopping for convergence.
    - Uses "global_mae" as metric key consistently (matches metrics.py, plots).
    - GPU-aware via DeviceManager.
  Issues:
    - get_green_duration() hard-codes a 45/55 ML/heuristic blend:
        duration = 0.45 * prediction + 0.55 * heuristic_optimal
      This means the ML model contributes LESS THAN HALF of the final decision.
      The published "FL improvement" is partly the heuristic, not purely ML.
      If the heuristic is removed, FL performance may degrade (but would be
      a purer ML result). This hybrid is undocumented in the paper.
    - get_green_duration() is DUPLICATED VERBATIM in centralized_ml.py.
      Should be a shared utility function.
    - federated_averaging() handles "quality_aware" inline with if/else, then
      delegates all others to robust_aggregate() — inconsistent dispatch pattern.
    - Memory accumulation: round_metrics list grows unbounded over 50 rounds
      (each entry stores per-round stats). Fine at 50 rounds.
  Interlinking: Core of run_ieee.py, run_byzantine.py. Depends on
               traffic_model.py, aggregation.py, device.py.

SECTION 3  —  SCALE ISSUES (performance at larger intersection counts)
================================================================================

ISSUE 1  GPU↔CPU transfers in FL loop                              SEVERITY: HIGH
  Location: src/models/traffic_model.py get_parameters()/set_parameters()
  Impact: Every FL round, ALL intersection models move GPU→CPU (aggregate)
          then CPU→GPU (broadcast). At 9 intersections × 50 rounds × 2
          directions = 900 transfers of ~400KB (FP32, [256,128,64,32] model).
          This is the single largest performance bottleneck.
  Fix: Keep parameters on GPU as torch tensors during aggregation. Convert
       to numpy only at final save / evaluation.

ISSUE 2  O(n²) distance computation in aggregation                SEVERITY: MED
  Location: src/federated_learning/aggregation.py _compute_distances()
  Impact: For n=9: 36 pairs — negligible. For n=100: 4950 pairs × parameter
          iterations — seconds per aggregation step.
  Fix: Use numpy broadcasting or scipy.spatial.distance.cdist.

ISSUE 3  time.sleep() in network simulation                       SEVERITY: MED
  Location: src/network_simulation/network_layer.py line 139
  Impact: Adds real wall-clock delay per model update transmission.
          Not active in IEEE experiments but affects run_with_ns3.py runs.
  Fix: Remove time.sleep(); track simulated latency as a metric only.

ISSUE 4  Sequential cloudlet execution in EdgeCloudSimulator      SEVERITY: LOW
  Location: src/cloudsim_python/edge_cloud_sim.py execute_cloudlet()
  Impact: 4 edge VMs execute sequentially — simulation_time advances
          linearly instead of showing parallel speedup.
  Fix: Track per-VM timelines independently.

ISSUE 5  list.pop(0) in Lane.remove_vehicles()                   SEVERITY: LOW
  Location: src/traffic_generator/intersection.py line 39
  Impact: O(n) per vehicle discharge. Fine at queue_length≤50. At 100+: slow.
  Fix: Replace list with collections.deque; use popleft().

ISSUE 6  Data re-generation at test time in local_ml.py          SEVERITY: MED
  Location: src/baselines/local_ml.py line 219
  Impact: Test MAE in local_ml evaluation uses freshly generated data,
          not a static held-out set. Makes Local-ML test MAE appear better
          than it is (same distribution, no test contamination but no
          true held-out evaluation either). FL and Local-ML should be
          evaluated on the SAME static test set for fair comparison.

ISSUE 7  Actuated controller phase timer bug                      SEVERITY: MED
  Location: src/baselines/actuated.py line 165
  Impact: phase_timer grows monotonically; never reset on phase switch.
          Actuated baseline performs worse than the real algorithm would.
          This inflates FL's apparent improvement over Actuated.
